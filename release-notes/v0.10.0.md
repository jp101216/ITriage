## New checks

- **Policy blocks** (`sec.blocks`). "The Dragon plugin won't launch" and "Save to Documents fails" usually come from one block event, not from a setting. This names the rule that did it over the last seven days: Defender attack surface reduction rules (named from Microsoft's GUID table), Controlled folder access, antivirus detections, AppLocker and App Control (WDAC) on Windows; AppArmor and SELinux on Linux. Repeats of one rule on one file are one row, with how many times and when. A block in the last day on an app the site profile requires is critical. Audit-mode rules are information: they stopped nothing. Enforced blocks also appear in the change timeline, so `--problem-at` lines them up with the reported time, and the slow-app runbook checks them.
- **Sign-in speed** (`desk.logon`, Windows). "Please wait for the Group Policy Client", explained: the last sign-in's profile load and user policy as one total (against 60 s and 120 s, set with `[thresholds] logon_seconds`), each Group Policy extension's time, the ones that failed, how many GPOs applied, and a domain controller that didn't answer (1129) or a SYSVOL file that couldn't be read (1058) during it. It reads one sign-in's own events by their ActivityID, so background refreshes can't push it out of the log. The sign-in runbook uses it.
- **Throttling & hardware errors** (`system.hardware`). The processor's clock against its maximum right now, judged against how busy it is (low and idle is power saving; low and busy is a limit), the firmware's speed-limit reports (event 37) with the time spent limited, and corrected or fatal hardware errors (WHEA). On Linux: cpufreq, the thermal-throttle counters and EDAC. It joins the **Health check** preset and the slow-PC runbook. The live HUD sample and recordings now carry the clock too.

The likely cause uses all three. A blocked app is named with the rule that blocked it. A slow sign-in names its slowest step ("Folder Redirection took 41.0 s of a 63.0 s sign-in"). A busy processor that's also being held back is reported as that, and the busiest program isn't blamed for it.

## Privacy

Case bundles now pseudonymize the user folder in the forms policy events write it (`%OSDRIVE%\USERS\NAME`, `\Device\HarddiskVolume3\Users\name`) and account SIDs.

## What was and wasn't run

The Windows field names come from each provider's own event manifest, read on a Windows Server 2025 runner. The Defender test uses a real captured event. The ASR, AppLocker, App Control, Group Policy, processor-power and WHEA tests use events written from those manifests, not captures: those checks still need a pass on a real workstation (see the lab steps in `docs/ideas/next-features.md`).

## Identity and trust

- **Certificate revocation** (in Machine certificates). An expired CRL on the issuing CA breaks 802.1X, VPN and smart-card sign-in for every PC at once, and Windows' cache can hide it. For each machine certificate in use, the CRL is now fetched live from each HTTP distribution point (through the system proxy) and its next-update time checked: expired is critical, expiring within `[security] crl_warn_hours` (24 by default) a warning, unreachable a warning. The chain engine's own verdict sits beside it (revoked, offline, unknown). LDAP distribution points are left to the chain check. With failing 802.1X in the same report, the likely cause says so.
- **Kerberos tickets** (in Entra, Kerberos & SSO sign-in, now on Linux too). The ticket cache through LSA: the TGT and when it expires, service tickets, the KDC, and tickets still encrypted with RC4 (or DES), which Microsoft is removing from domain controllers. Servers that rejected a ticket (event 4, KRB_AP_ERR_MODIFIED, a duplicate SPN or stale password) are critical. Tickets belong to a sign-in, so they're only read when ITriage runs as the signed-in user, unelevated; otherwise it says so rather than reporting the administrator's. On Linux: MIT `klist -e`.
- **Clear Kerberos tickets**, a new fix (`purge-kerberos-tickets`): `klist purge` for the session ITriage runs in, or `kdestroy`. It refuses when elevated, as another user or as root.
- **Fix previews.** `itriage --fix ID --what-if` says what a fix would do here and changes nothing, after the same policy checks a real run makes. The confirmation dialog shows it too (the Kerberos fix says how many tickets it would clear).

## The audit trail

- **Hash chain.** Each line of `audit.jsonl` carries the SHA-256 of the line before it, across rotation. `itriage --verify-audit` walks it and names the first line that was changed, removed or inserted (exit 1). Lines from 0.9 and earlier aren't chained and are counted separately.
- **Refusals have their own event**, 1102, apart from failures (1101). Each event's last line carries the ticket, the account and whether it ran elevated. The existing IDs (1000, 1001, 1100, 1101) are unchanged, so SIEM rules keep working.
- **The installers register the `itriage` event source**, so events render cleanly in Event Viewer from the first run, even one that never runs elevated. It's left in place on uninstall, so the events already logged stay readable.
- On Linux the copy goes to syslog through `syslog(3)` instead of running `logger`.
- `[audit] event_log = false` turns the system-log copy off, but only in a managed profile: a user's own profile can't hide what a technician did.
