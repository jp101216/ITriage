Three checks for tickets every hospital service desk gets and ITriage couldn't explain until now: "I signed in and everything's gone", "the update keeps failing", and "the app from Intune never arrived". Plus a Sync with Intune fix, and likely-cause lines for all of them. Includes everything in v0.11.0.

## User profile & FSLogix

**User profile & FSLogix** (`desk.profile`, Windows) explains a temporary profile, and what an FSLogix container is doing.

- **Temporary profiles.** It catches a temporary profile for the person signed in, and finds profiles Windows set aside as `<SID>.bak` (each of those accounts gets a temporary profile until it's sorted out).
- **What kept the profile from loading.** Windows names the program that had a profile's `NTUSER.DAT` open (events 1545 and 1552), and ITriage shows it: "Program holding a profile's registry file: BackupAgent.exe".
- **A week of load failures** (1500, 1502, 1508, 1542), with Windows' reason and the file. Windows retries a failed load dozens of times in a few seconds; that counts as one attempt, not dozens.
- **FSLogix**, when it's installed:
  - Profile Container on or off, its VHD or Cloud Cache locations, and the `frxsvc` service.
  - This sign-in's Status, Reason and ErrorCode, decoded with Microsoft's tables. A local profile that's keeping the container out is called out.
  - The attached container's free space.
  - FSLogix's own events: nearly full (33/34), in use on another machine (39/51), no location set (40), the share unreachable (43), and attach or sign-in failures (41/52).

## Why updates fail

**Why updates fail** (`update.history`, Windows) reads Windows Update's own history, the same list as Settings → Update history. It's local; nothing is downloaded.

- **One row per update that keeps failing.** Each one shows how many times it failed in 90 days, when it last failed, and its last error code. Three failures is critical.
- **What the code means.** About 50 codes are explained with the name, cause and next step Microsoft gives on its Windows Update error pages. A code that isn't in that list is shown as a number, with no guess.
- **The next step.** Component store corruption (0x800F081F, 0x800F0831, 0x80073712…) points to **Clean up & check system files**. Proxy and network codes point to the update source, and disk-full codes to free space.
- Updates that failed and have installed since are listed separately, so they don't raise an alarm. Definition updates count together by KB number.
- Added to the **Health check** preset.

## Intune enrollment & apps

**Intune enrollment & apps** (`desk.intune`, Windows) shows what the PC itself knows about Intune.

- **Enrollment.** Intune's own enrollment is recognised. Windows keeps built-in enrollments even on PCs nothing manages, and those aren't mistaken for Intune.
- **The last syncs**, from the DeviceManagement Sync log: when, and how each one ended. It warns after a day without a successful sync, or when the last one failed, and goes critical after a week.
- **The Intune Management Extension service**, and the week's MDM errors.
- **Win32 apps that failed to install**, by Intune app ID (the PC doesn't record their names), with the error explained where Microsoft documents it.
- **Compliance isn't shown.** It's decided by the Intune service and isn't stored on the PC in a documented form.

**Sync with Intune** is a new one-click fix (administrator). It starts an MDM sync through Windows' `MdmSessionManager` API, then restarts the Intune Management Extension. Microsoft documents that restart as starting its app check-in. It's offered when the sync is stale or failed, and on a failed app.

## Likely cause

New lines for:
- a temporary profile, naming the program that held the profile's file;
- FSLogix stopped, not attached (with the fix for a local profile in the way), nearly full, or in use elsewhere;
- an update that keeps failing, explained by its code;
- a PC that hasn't synced with Intune for a week;
- Intune apps that failed.

## Upgrading

Nothing in an existing site profile needs to change.

- The new checks are read-only and appear in the list like any other.
- **Sync with Intune** is offered unless a profile's `fixes` list leaves it out. The example clinical profile now lists `sync-intune`, plus `start-service:frxsvc` and `start-service:IntuneManagementExtension`.

## Checked

- 402 core tests on Linux and 395 on Windows, 26 browser tests, workspace Clippy, and the smoke checks and installer builds on both platforms.
- **A real temporary profile, every CI run.** A new Windows CI step loads a test account's profile while PowerShell holds its NTUSER.DAT open, which is how it happens in the field. Windows logs 1508, 1545, 1502, 1515 and 1511 and sets the profile aside as `.bak`. User profile & FSLogix then has to report the `.bak`, the temporary sign-in, powershell.exe as the program holding the file, and one load failure with its file.
- **Real update history and enrollments.** In the same step, Why updates fail reads the runner's update history through Windows Update, and Intune enrollment & apps has to read the runner as not enrolled, despite Windows' built-in enrollments.
- **Real event definitions.** Event IDs, fields and messages were taken from the event definitions Windows and FSLogix install, on such a runner, for the User Profiles Service, Windows Update, MDM and FSLogix.
- **A real FSLogix install.** On a runner with FSLogix 3.26.826 installed and turned on, ITriage read its version, locations and own events, and flagged a stopped `frxsvc` as critical with its fix.

## Not yet run

- **FSLogix with a real sign-in.** A test runner can't attach a container, because only an interactive sign-in does. So "attached", "full" and "in use elsewhere" have been tested against Microsoft's code tables and FSLogix's own event text, not a live container.
- **An Intune-enrolled PC.** This covers the Sync log, the Win32 app results and Sync with Intune itself. The app results' registry layout isn't documented by Microsoft; it follows MSEndpointMgr's write-up, and anything that doesn't match is skipped.
- **An update that really failed.** The runner's history has only successes, so the grouping and the code meanings are covered by unit tests.

What 0.10.0 and 0.11.0 list as not yet seen on a clinical workstation still stands.
